# shinobi -- design conventions

Spiritual successor to Stimela classic, reacting against Stimela 2.0's YAML-recipe complexity. Read this before changing the recipe/orchestration layer, but read it as a set of durable guardrails and pointers, not as a substitute for the maintained documentation or source contracts.

Organisation-wide conventions live in
[`shinobi-dosho/.github`](https://github.com/shinobi-dosho/.github/blob/main/AGENTS.md) -- this file states what is
specific to `stimela-ninja` and wins where the two disagree.

## Sources of truth

For current behaviour and design, use the maintained material in this order:

1. The user and design documentation under [`docs/`](docs/), especially [`docs/design.rst`](docs/design.rst) and the relevant concept page.
2. The docstrings on the public type or function and the module-level docstring that explains its invariants.
3. This file, for cross-cutting guardrails, implementation traps and historical rationale.

Verify all three against the working tree and tests before changing behaviour. If this file conflicts with the docs or a current source contract, do not make the implementation conform to a stale sentence here: update this file, or ask the maintainer when the intended contract is genuinely ambiguous. Historical design notes describe how a feature was arrived at; the maintained docs and docstrings describe what shipped.

## Core rule

**A constructed `Recipe` is a declared DAG.** Its `steps` and explicit `InputRef`/`OutputRef` wiring are data that `build_graph()` can validate and render before dispatch. `after` adds an ordering-only edge. `add_loop()` is the deliberately admitted run-time conditional: it unrolls a bounded body while building the recipe, then an already-declared step may short-circuit. Every possible node and edge still exists before execution.

That rule governs the graph's shape; it does not forbid ordinary Python. Recipe builders may use Python and validated configuration to decide which nodes to declare. A step body may also be an orchestration function bound by `@shinobi.step`/`@recipe.step`: it receives an `ExecContext` and may retry, post-process, or call `ctx.run()` more than once. Such behaviour is intentionally opaque inside one graph node and makes that step ineligible for compile-and-offload. Use `add_loop()` when repetition is pipeline structure that should remain visible; use an orchestration function when the behaviour belongs inside one step. Local-only functionality is a supported part of the model, not a violation of the declared-DAG rule.

`Recipe` and `Cab` extend `Scope` (schema, metadata and execution configuration). `StepRef` binds a scope to a name, optional orchestration function, wiring and per-step constants; it is what both decorators return. `ExecContext` is live execution state. String step names are deliberately admitted because names are the natural addresses in graph data; field names live inside explicit reference objects and are validated against the pydantic models.

Do not add:
- A string-based expression/substitution language for referencing other steps' params or outputs (e.g. stimela2's `=recipe.ms`, `{recipe.name}-{info.suffix}`). Wiring uses explicit `InputRef`/`OutputRef` objects whose field names are validated against the models.
- An alias-propagation system. Stimela2's DEVNOTES.md describes multi-pass up/down propagation logic to keep step and recipe-level params in sync, plus glob re-evaluation hacks to work around it. That entire class of problem only exists because YAML was the orchestration layer. Don't recreate the problem.
- A second orchestration language in YAML. YAML configuration may be validated and used by Python to build a `Recipe`, and a thin compiler may emit the same graph, but markup must not acquire its own expression evaluator, run-time control flow or alias resolver.

**This is an orchestration boundary, not an objection to markup or composition.** Static YAML/JSON cab schemas, `AppConfig`, worker configuration, and the supported `_include`/`_use` schema-composition directives are data. Package-scoped includes must resolve through caller-supplied filesystem roots and must never import a named package. `ParamMeta.implicit`, `harvest` and `scratch` deliberately allow plain `str.format` against the current step's validated inputs. They may derive local values and paths; they may not call functions, evaluate conditions or address another step. `dynamic_schema` remains unexecuted because loading a schema must not import and call code named by untrusted markup. See [`docs/concepts/loaders.rst`](docs/concepts/loaders.rst), [`docs/concepts/results.rst`](docs/concepts/results.rst) and [`SECURITY.md`](SECURITY.md).

## DRY

Before writing logic that resembles something already in the codebase, look for it first -- grep for the behavior, not just the name, since the existing copy may use different naming. Shared logic belongs in one place with every caller routed through it, not reimplemented per call site; this applies everywhere, not only to the loaders (see `_modelgen.py`'s `resolve_use`/`validate_choices`/`COMMON_LEAF_KEYS` below for a concrete case where two loader dialects had quietly drifted into near-identical private copies of the same rule). A second near-identical implementation of an existing rule is a bug waiting to happen the moment one copy gets fixed/extended and the other doesn't -- treat spotting one as a prompt to unify, not to leave both as "close enough."

## What's worth keeping (and why)

- **Typed cab schema** (`shinobi.Cab`): pydantic-model inputs/outputs (`inputs_model`/`outputs_model` -- generated model classes, not hand-written dicts), with `flavour`, `image`, `Policies` (prefix/replace/list_sep/repeat_list -- auto-generate CLI args), `field_meta` (per-field `ParamMeta`: `nom_de_guerre`, `implicit`, `info`), and `input_patterns`. This declarative schema is genuinely better than Stimela classic, which required a hand-written `run.py` per cab to build argv imperatively. File-like dtypes (`File`/`MS`/`Directory`/`URI`) map to `pathlib.Path`; `path_fields(model) -> set[str]` (unwraps `Optional`/`list`, handling both `typing.Union` and `X | None`) drives both `bind_dir_modes` and CLI `click.Path()`. Loaders (`shinobi.loaders._modelgen`) build the models via `pydantic.create_model`, sanitising non-identifier param names (hyphens/dots common in cult-cargo/classic) to valid field names and keeping the original as a `nom_de_guerre`.
- **Pattern-matched dynamic fields** (`shinobi.steps.ParamPattern`, `ParamSegment`, `Cab.input_patterns`/`output_patterns`): some tools have field names containing caller-selected segments, so no static model can enumerate them. A pattern is an anchored sequence with exactly one literal `attrs` segment (each value carrying `ParamMeta`) and regex shape segments for the open parts. The `attrs` segment may occur anywhere: input families commonly end in a known attribute, while WSClean output families begin with a known image type. Use a lazy regex such as `.+?` for an unconstrained segment so a longer attribute containing the separator wins. `_prepare_inputs` retains allowed model extras; `build_argv()` emits matching input extras. Output patterns validate dynamic output references but do not populate arbitrary result fields; use a literal output, `implicit`, a wrangler or `harvest` for that.
- **YAML cab compatibility, the scabha dialect** (`shinobi.loaders.yaml_cab`): shinobi's cab schema is borrowed from scabha (Stimela 2.0's schema library), and cult-cargo is the largest published library written in it. The cab schema format itself isn't the problem -- only the recipe layer built on top of it is. Loading existing cult-cargo cab defs unlocks the whole existing radio-astronomy tool library instead of requiring a rewrite. Some real cult-cargo cabs carry non-`"binary"` flavours whose `command` is executable code, not a program name -- see [`SECURITY.md`](SECURITY.md) for how that's handled.
- **stimela-classic `parameters.json` compatibility** (`shinobi.loaders.stimela_classic`): a second, unrelated cab schema format (one JSON file per cab, no `_include`/`_use` composition to resolve) -- useful for exactly the tools cult-cargo doesn't have a loadable definition for (several CASA tasks, `msutils`; see `examples/ninja_selfcal.py`'s module docstring for which ones and why). Verified against real files (`casa_mstransform`, `casa_listobs`, `casa_flagdata`, `casa_flagmanager`, `msutils`, `wsclean`, `cubical`, `breizorro` all load cleanly). Classic's CASA-task cabs (`base` containing `"casa"`) load as `flavour="casa-task"`, not `"binary"` -- their `binary` field is a CASA task name invoked by wrapping it in a CASA script, not a real standalone executable, so loading them as `"binary"` would let `UnsupportedFlavourError`'s guard down for something that would still misbehave if actually run. `choices` (`ParamMeta.choices`) narrows the generated model field's real annotation to `typing.Literal[*choices]` (`shinobi.loaders._modelgen.narrow_choices`, shared with `cultcargo`/`worker_schema`), so an out-of-set value fails real pydantic validation, not just a note in `info` (classic's loader also still appends a human-readable `(choices: ...)` parenthetical to `info`); a `dtype` declared as a list of alternatives (a real type union) is narrowed to its first alternative.
- **Loader dialects share structure** (`shinobi.loaders._modelgen`): `cultcargo` (a *cab* schema) and `worker_schema` (a *config* schema) both parse a scabha-derived YAML dialect and used to carry near-identical private copies of the same rules -- `_use: dotted.path` resolution, `choices`-is-a-list validation, the base set of keys marking a node as a leaf param rather than a nested group. Unified into `_modelgen.resolve_use`/`validate_choices`/`COMMON_LEAF_KEYS` per the DRY principle above; each loader-specific extra (cultcargo's `nom_de_guerre`/`mkdir`, the exact `_include` entry shapes each dialect accepts) stays local, since that part is a genuine dialect difference, not shared structure. **Package-scoped `_include` resolution is shared and must stay that way**: `_modelgen.resolve_package_root` maps a dotted package name onto a caller-supplied `package_roots` filesystem mapping, and neither loader may resolve one by importing the package. `worker_schema` used to do exactly that (`importlib.import_module` on a module name read out of a YAML file, i.e. arbitrary `__init__.py` execution at schema-load time) while `cultcargo` refused to -- one loader implementing a documented security guarantee and its sibling silently breaking it. Sharing the helper is what stops that drifting apart again; see SECURITY.md's "never import a cab package".
- **Config-schema groups with config-supplied keys** (`shinobi.loaders.worker_schema`'s `_each`): every other group in the dialect declares its keys in the schema; `_each` declares one sub-schema and lets the *config* supply the names (caracal2's calibration chains, where the whole point is that a user can add one). It produces `dict[str, <SubModel>]`, with an optional `_key_pattern` regex constraining the names -- set it whenever those names become step names or path components, since the alternative is a name that breaks a run far from the config that supplied it. Two things are deliberate: the `_each` test runs **before** the leaf test (such a group normally also carries `info`/`default`, which are `COMMON_LEAF_KEYS`, and would otherwise be read as a `str` param), and the `default:` mapping is validated at load and rebuilt per instance rather than shared. The CLI cannot express these fields at all -- `clickutil.iter_leaf_fields` skips them, because there is no fixed set of names to build flags from.
- **Output wranglers** (`shinobi.wranglers`): regex-based extraction of structured outputs from a cab's console output. Only `PARSE_OUTPUT` is implemented; add other actions (`HIGHLIGHT`, `SUPPRESS`, ...) only when a real cab needs them, not speculatively.
- **Backend abstraction** (`shinobi.backends`): a step doesn't know if it's running natively, in a container, or on a cluster. Backends shell out to the runtime CLI (`docker`/`podman`/`apptainer`/`sbatch`+`sacct`/`kubectl`) rather than using each system's Python SDK -- one code path per backend, no heavyweight client dependencies, and it's the only option for runtimes like apptainer that don't have a good Python API anyway. The dispatch layer (`_run_cab`) pre-builds argv via `shinobi.policies.build_argv()` and hands it to `Backend.run(cab, argv, inputs) -> BackendRun` -- backends receive argv ready-made, so slurm/k8s reuse it directly. `inputs` is the *prepared* inputs dict (not a rebuilt model), so MUTABLE fields reach the backend as the caller's own objects by reference. Container/cluster backends derive bind mounts from the schema via `path_fields()`: any input field whose type is file-like (`pathlib.Path`) gets its parent directory mounted at the same path (`bind_dir_modes`, shared between container and kubernetes backends). **Inputs alone are not enough**, and assuming they are is a silent-data-loss bug, not a gap: a tool's output *stem* is conventionally a string-typed input (wsclean's `prefix`) precisely so that `sandbox.absolutize_path_inputs` leaves it relative, so it contributes no path field and no mount -- point one at an absolute directory the inputs don't cover and the tool writes into the container's own filesystem, which `docker run --rm` then destroys on exit (a *green* step with no product; apptainer instead fails opaquely on its read-only image). The write target is declared on the output side, and `schema.declared_output_dirs` is the single reader of it (a path-typed output's value/`implicit` template, plus each `harvest` pattern's literal prefix, resolved pre-run): `sandbox.prepare_output_parents` takes the relative half, `bind_dir_modes` the absolute half. Keep it one function -- the two halves are complementary filters over the same declaration, and a second copy would drift the moment either side learns a new way to declare an output. Value-shape heuristics on `str` fields are deliberately **not** used (a TaQL string or a column name can look like a path); a cab that declares no output for a stem gets no mount, by design. Where anything that must be writable — a write target, another input, or the workdir — collides with a `writable: false` input **neither declaration may be dropped** — the directory goes read-write and each read-only input inside it is re-asserted `:ro` at its own path (nested mount). "Writable wins" now applies to the *directory* only; the read-only input beside it is no longer collateral, which retires the `in-place MS in a writable msdir` carve-out (that MS still mutates — verified live on docker — and its read-only neighbour is now protected too). Note what that does and does not protect: `Mutability.IMMUTABLE` is a *Python-object* guarantee (deepcopy in `_prepare_inputs`) and never stopped a tool writing a file; `writable: false` is the only filesystem one, so letting an output declaration silently override it would have been the actual hole. Nested shadowing was verified on real docker, podman (rootless), apptainer **and a real kubelet** (`readOnly` volumeMounts on a kind cluster, pod running as root so only the mount could refuse), in both emission orders and for file- and directory-valued inputs; the returned list is ordered parent-before-nested regardless, so a runtime honouring order rather than depth still gets it right. What nesting canNOT resolve is something writable inside a read-only input's *own* path (a write target, a writable input, or the workdir) — "never write this" and "put a product here" over one tree — which is refused on every backend rather than silently mounting that input read-write (the review catch on #62: `readonly_paths` is keyed by *parent*, so a brand-new mount key that happens to BE a read-only input path recorded no upgrade and slipped through). Every backend's `run()` blocks until the job/container/process is done and returns a `BackendRun` (`returncode`, `stdout`, `stderr`) -- there's no async/fire-and-forget mode, because the next step usually needs this step's output.
  - `native`/`docker`/`podman`/`apptainer` were verified against a real `quay.io/stimela/wsclean` image and a real bind-mounted host file in `tests/test_docker_live.py` (skipped if docker/the image isn't available) -- not just mocked.
  - `venv` (`backends/venv.py`) runs a cab (or a `@pystep`, sharing the container path's out-of-process runner in `steps/pyfunc.py`) inside an existing Python virtualenv: `native` plus an activated env (`VIRTUAL_ENV`/`PATH` set, `PYTHONHOME`/`PYTHONPATH` cleared), with `argv[0]` rewritten to the venv's own copy of the tool when present. It's a deliberately weaker *complement* to containers (no fs namespace, no OS-level pin), for the pip-installable half of a pipeline. The venv is named on a `Scope` (`venv=`) or in config (`backend.venv`), never in cab YAML (a venv path is machine-specific). Provenance is a `venv_digest` (sha256 of the venv's `name==version` list) recorded only under `pin=True`, but a venv step is **always reported unpinned** (`RunManifest.pinned`) -- the digest is version-parity, not an image pin -- so `ninja replay` refuses a venv-containing manifest unless `--allow-unpinned`. `check_offloadable` rejects venv steps rather than letting them mis-run natively on a compute node. Selecting `venv` with no venv declared anywhere degrades to native/in-process with a warning.
  - The blocking `slurm` step backend and compile-and-offload Slurm path have both been verified against a real single-node cluster. Automated live coverage exists for the offload path (`tests/test_slurm_live.py`); the step backend's automated tests mock `sbatch`/`sacct`. Multi-node scheduling and shared storage remain site-specific and unproven. The Kubernetes backend has live coverage against `kind`; its `hostPath` volumes require the chosen node to have the path, so they are suitable for a single-node dev cluster or nodes with shared storage, not general multi-node storage. Kubernetes requires an explicit namespace, applies `writable: false` through `bind_dir_modes`, and emits a restricted pod `securityContext`.

## Architecture summary

- **Result plumbing** (`shinobi.results`): `_run_cab` applies wranglers to a `BackendRun`'s stdout+stderr, fills `outputs_model` fields by priority (wrangler value > same-named final input > reserved names `returncode`/`stdout`/`stderr` > resolved `ParamMeta.implicit` > field default), validates, and wraps everything in `StepResult` (`name`, `returncode`, `stdout`, `stderr`, `outputs: BaseModel`, `inputs: BaseModel` -- the effective post-override inputs, `.success`). For a `Recipe` these aggregate from sub-steps. `OutputRef` resolution reads `results[ref.step].outputs.<field>`.
- **`@shinobi.step` decorator** (`shinobi.step`): binds an orchestration function to a `Scope` (Cab or Recipe), returning a `StepRef` -- the single carrier of the function (no global registry). The function takes `ctx` (an `ExecContext`) and returns either the `StepResult` from `ctx.run(**overrides)` or `None` (auto-run); anything else raises `TypeError`. `@recipe.step` is the same, appending the StepRef to `recipe.steps`. The function's signature is **not** introspected -- the pydantic models on the Scope are authoritative. Everything flows through `_dispatch(scope, func, ...)` (in `shinobi.steps.dispatch`); `Scope.__call__` dispatches with `func=None`. Backend resolution priority: explicit arg > scope's own `backend` > enclosing recipe's backend > `AppConfig.load().backend.default`.
- **`@shinobi.pystep` decorator** (`shinobi.steps.pyfunc`): the opposite tradeoff from `@shinobi.step` -- for a plain, type-hinted Python function with no external tool and no existing `Cab`/`Recipe`, it derives `inputs_model` from the function's own signature (`inspect.signature` + `typing.get_type_hints`, not `param.annotation` directly, since every module here uses `from __future__ import annotations`) and `outputs_model` from its return-type annotation (a `BaseModel` subclass, used directly and returned as-is; no annotation/`-> None` means no outputs; anything else is rejected at decoration time rather than auto-wrapped into an invented field name). It builds a bare `Scope` (not a `Cab`, not a `Recipe`) and wraps the function in an adapter that returns its own `StepResult` directly, never calling `ctx.run()`. v1 has no per-parameter mutability override (every field is `IMMUTABLE`, the `Scope` default) -- add one only if a real function needs it. `Recipe.add_step` accepts the resulting `StepRef` directly (not just a bare `Scope`/`Cab`/`Recipe`), carrying its `func` over, so a pystep wires into a Recipe the same way a Cab does.
  - **Manual/"purist" alternative**: a bare `Scope(name=, inputs_model=, outputs_model=)` built by hand, wrapped in `StepRef(name=, step=, func=)` where `func` builds and returns its own `StepResult` (never calling `ctx.run()`, which only knows `Cab`/`Recipe` and raises `TypeError` for anything else) is the same underlying mechanism with none of the signature-introspection magic -- use it if you'd rather not have `@shinobi.pystep` infer the schema for you. See `Scope`/`StepRef`'s docstrings in `schema.py`.
- **`ninja run <target> [OPTIONS]` CLI** (`shinobi.cli`): a thin argv-to-kwargs translator for `Cab`/`Recipe`/`StepRef` targets. `<target>` is `path/to/file.py:name` or `dotted.module:name`, resolved via `importlib`; the target's `inputs_model.model_fields` are turned into `click.Option`s *at runtime* (the target isn't known until the CLI parses it -- this needs the underlying `click.Command`/`click.Option` object API directly, since declarative `@click.option` is fixed at import time). `ninja` is the sole console-script entry point (PyPI/distribution name `stimela-ninja`); `shinobi` stays the importable library name only -- there's no `shinobi` command.
- **DAG execution** (`shinobi.graph` + `_run_recipe`): a `Recipe` is a declared DAG, and both the executor and the `--dryrun` renderer read it through **one** builder -- `shinobi.graph.build_graph(recipe) -> RecipeGraph` -- so they can never disagree on edges or validity. `build_graph` validates every wiring reference (`InputRef` field exists on the recipe's `inputs_model`; every `OutputRef.step`, in a step's wiring *and* in `output_wiring`, is a real step), rejects duplicate step names, and rejects dependency cycles (`graphlib.TopologicalSorter`, whose `CycleError` names the cycle itself -- draining in-degrees by hand reported the cycle *plus everything downstream of it*, burying the two steps actually pointing at each other) -- all raising `RecipeGraphError`. It runs at run time and at dryrun time, **not** at build time (a `Recipe` is mutable through its builders, so a forward `OutputRef` mid-construction is legitimate). `RecipeGraph.deps` are the *true* `OutputRef` edges (no artificial chaining); `dependents` is the precomputed reverse set. `_run_recipe` (`steps/dispatch.py`) schedules a **topological wavefront** over a `concurrent.futures.ThreadPoolExecutor` (threads park on the blocking `Backend.run`; there is no async mode) -- a step becomes ready only once every step whose output it wires in has completed, and the ready set is drained lowest-declaration-index first so `max_workers=1` reproduces exact sequential declaration order. On the first non-zero returncode *or* worker exception it stops submitting but lets already-running steps drain (a launched job/container can't be honestly cancelled through a Future). Aggregation (stdout/stderr concatenation, `output_wiring`, the winning returncode = first failure by declaration index; a worker exception re-raised is likewise first-by-declaration) is done in **declaration order regardless of completion order**, so results are deterministic. `max_workers` resolves `recipe.max_workers or config.execution.max_workers` (default **1** -- parallelism is opt-in), the same two-layer precedence shape as `backend`; no CLI flag (keep the precedence at two layers). `_run_recipe` resolves `AppConfig` **once** and threads the instance down (`_config=`), so worker threads never call the `ClassVar`-mutating `AppConfig.load()`. **Resource-aware admission** (`shinobi.resources`): `max_workers` counts slots and says nothing about cost, which is a poor fit for steps each sized to use most of a machine. A `Scope` may declare a `Resources` footprint (`cpus`/`memory`), and `_run_recipe` then admits work against a `Budget` as well as a slot count. Four things are load-bearing and easy to get wrong if this is ever refactored. (1) **One budget per run, shared by every nested recipe's scheduler**, threaded down like `AppConfig` (`_dispatch(_budget=)`): caracal-shaped pipelines nest each parallel branch as its own `Recipe`, so a budget scoped to one `_run_recipe` invocation is a no-op exactly where it is needed. (2) **`detect_budget` walks the full cgroup ancestor chain**, not the leaf -- the quota that matters usually sits several levels above the cgroup a process runs in, and reading only the leaf falls through to `/proc/meminfo` and reports the host's memory, silently recreating the bug this prevents. (3) **The scheduler's main loop gates `pending`/`ready` on `not stop`** (`while futures or (not stop and (pending or ready))`); dropping that gate makes a failure hang instead of draining, and it bites recipes that declare nothing. (4) **Reservations are returned on every exit path** via an `ExitStack` callback registered before the pool, because `_expand` runs on the scheduler thread and can raise straight past the reap loop -- and a leaked reservation against a shared budget throttles every sibling for the rest of the run. Admission blocks in declaration order with FIFO tickets across sibling recipes (so a large step can't be starved); a demand exceeding the whole budget is granted immediately rather than parked, since waiting could never make it fit; an undeclared step is free. **Backfill** (`Budget.try_backfill` + `_backfill_behind`) then recovers the capacity that blocking on the head would otherwise idle -- a 200 GiB step at the front of the queue should not stop the 2-core steps behind it -- by admitting a trailing unit only when the parked head would still fit *alongside it* once the work reserved now drains, so the head waits for exactly what it was already waiting for. Three things here are load-bearing. (1) **The test is cumulative**: bounding each grant against the total on its own admits two 30 GiB units in a 100 GiB budget behind a 70 GiB head, and the head then cannot start when the original holder finishes -- so `Budget` tracks outstanding backfill separately and `release(demand, backfilled=)` must match how the grant was made, or the counter drifts and backfill silently stops. (2) **It is not `try_acquire` with a flag**: that call refuses on FIFO fairness (which backfill must keep honouring) but *pops the caller's ticket* on a grant, and the caller is the very scheduler thread holding the head's place in the queue. (3) **Gated on `max_workers > 1`**: with a shared budget a sibling recipe can leave this scheduler with nothing in flight and a refused head, and backfilling there would break the guarantee that `max_workers=1` reproduces exact declaration order. A candidate whose declaration index is *lower* than the head's is not a backfill at all -- it outranks the head, so it is expanded unconditionally and becomes the next head. Declaring resources on a nested `Recipe` is rejected by `build_graph` -- a recipe is not a unit of execution, and reserving for both it and its leaves would double-count and deadlock. The same declaration feeds real enforcement at the backends (`--cpus`/`--memory` for docker/podman/apptainer, k8s requests==limits, `#SBATCH --mem`/`--cpus-per-task`); `native`/`venv` have no backstop at all. Resources are deliberately **not** part of the cache key (unlike `venv`, they change how a command is constrained, not which command runs) and **not** restored by `apply_manifest_pins` (a footprint describes the box, not the run). **MUTABLE hazard**: at `max_workers > 1`, two independent steps that wire in the *same* MUTABLE input run concurrently against that shared object -- a data race shinobi cannot detect and deliberately does not "fix" by deep-copying (that would break the MUTABLE pass-by-reference contract); IMMUTABLE inputs (the default) are deep-copied per step and are safe, and the default `max_workers=1` never exposes the race.
- **Scatter/fan-out** (`StepRef.scatter`/`ScatterSpec`): a step can declare that one or more of its input fields are list-typed at the recipe level and should be fanned out over at runtime. The step's own `inputs_model`/`outputs_model` describe a single slice; `_run_recipe` expands the scatter into N parallel `_dispatch` calls (each slice gets the element at the same index of every scattered field), gathers the per-slice outputs into lists, and only releases downstream dependents once every slice has completed. A downstream step can scatter over the gathered list in turn or consume the whole list as a single input. `build_graph` validates that scatter fields exist on the step's `inputs_model`; runtime enforces that all scattered fields are lists of the same length. Scattered recipes are **not offloadable** in v1 (cluster engines would need to know N statically, and the inter-step data flow is a list of values rather than a single path).
- **Declared loops** (`Recipe.add_loop` + `shinobi.steps.loops`): bounded unrolling with short-circuit pass-through, for the one thing a declared DAG genuinely couldn't express -- "keep self-calibrating until the fidelity stops improving". `add_loop(name, body, max_iter=, until=, carry=, index_input=)` **flattens** the body into the parent recipe once per iteration (`selfcal.3.image`) and chains the copies with the explicit `carry` wiring, so the result is an ordinary statically-inspectable graph: `--dryrun` renders every iteration, `build_graph` validates it, and the offload compiler emits a plain `afterok` chain. `until` names a **path**-typed body output whose *existence* means converged; `shinobi.steps.loops.should_skip` is the single definition of the rule, applied in-process by `_run_recipe` and compiled into a `[ -e ... ] && exit 0` guard by `compile_slurm` -- a path rather than a bool precisely so both tiers can evaluate the identical predicate (a bool cannot cross a node boundary). A skipped step returns the *same body step's* previous-iteration `StepResult` unchanged (so convergence is sticky for free, since the sentinel is itself one of those outputs), marked `skipped=True` but keeping its real `kind` -- inventing a "skipped" kind would break `apply_manifest_pins` and make every early-converging run unreplayable.
  - **Why this is admissible where an orchestration function is not.** A `for … if converged: break` inside a `@shinobi.step` function expresses the same thing in less code, and was deliberately rejected: it is *opaque* to `build_graph` (no iteration count, no internal wiring, one node in `--dryrun`), and offloading it would mean running arbitrary user Python on compute nodes -- which `check_offloadable` rejects for good reason. Unrolling is a strictly weaker form of runtime conditionality: every node is declared, wired and validated ahead of time, and the only run-time decision is whether an *already-declared* node does work. That is the line. `--dryrun` therefore shows what is **declared**, not what will run; the run manifest records which iterations were `skipped`, and that is where you look for what actually happened.
  - The body must be a **fixed point** (its outputs re-consumable as its inputs, via `carry`). `carry` is mandatory and explicit -- defaulting it to same-named fields would make the graph's shape depend on name coincidence, which is the alias propagation this project exists to avoid. `index_input` binds the 1-based cycle number, the one input that deliberately differs between iterations; without it every iteration resolves identically and a body cannot name outputs per cycle. A body naming outputs per cycle runs **locally** (`_fill_outputs` resolves `implicit` templates against real inputs) but is **rejected by `compile_slurm`**, since such a path isn't statically knowable -- an honest `OffloadCompileError`, not a silently wrong path. Consequently every path an offloaded loop carries is iteration-invariant, which is why a skipped sbatch job needs to materialise nothing and is a bare `exit 0`. v1 rejects a body containing `scatter` or a further nested `Recipe`.
  - **`StepRef.after`**: ordering-only edges (no data flows), folded into `deps` by `build_graph` like any wiring edge. Introduced because an iteration's *entry* steps read nothing from their own iteration, so the `carry` alone would let them start before the previous iteration's sentinel had been decided -- and under offload they'd carry no `afterok` link at all. Not an escape hatch for arbitrary sequencing: prefer real wiring wherever a value actually flows.
- **DAG offload / compile-and-offload** (`shinobi.offload` + `shinobi.graph.check_offloadable`): the *second* orchestration tier, for cluster-level distribution. Where local execution (`_run_recipe`) holds the whole DAG in one babysitting process, offload **compiles the declared `RecipeGraph` into a native cluster engine's workflow and detaches** -- so the cluster runs the graph even if the client disconnects (the motivating need: long HPC runs). It is a *sibling* of dispatch, not part of it: a `ninja compile <recipe> --engine slurm [--submit]` CLI over the same `build_graph`, mirroring `--dryrun`'s shape; `ninja status <handle>` reconstructs a detached run's progress by querying the engine fresh (no persistent process). This only works for a **restricted subset** of recipes, enforced by `check_offloadable(recipe)` (a sibling of `build_graph`, raising `RecipeNotOffloadableError` with *all* reasons at once): no orchestration functions, every step a `binary`-flavour `Cab`, no MUTABLE *non-path* inputs, and every **inter-step** `OutputRef` carrying a **path** output that isn't wrangler-derived -- because across nodes data flows only as shared-filesystem paths and shinobi never sees an offloaded step's stdout. Compilation rejects anything outside that subset; the same recipe may still be valid for local `ninja run`. `output_wiring` (the recipe's own outputs) is deliberately *not* checked -- it's a reporting boundary, not inter-node data flow. **v1 target: Slurm dependency chains** (`shinobi.offload.slurm`): `compile_slurm(recipe, inputs, ...)` is a **pure** function (recipe+inputs -> a `SlurmWorkflow` of `afterok`-linked sbatch scripts; golden-testable, no cluster), resolving each inter-step path statically from the producing step's same-named-input passthrough or output-field default (mirrors `_fill_outputs` minus the backend run; an unresolvable path is a hard `OffloadCompileError`). `submit_slurm`/`status_slurm` shell out to `sbatch`/`sacct` and are **live-verified single-node** against a real Slurm controller (`tests/test_slurm_live.py` + the throwaway all-in-one cluster in `tests/slurm_live/`, skipped unless it's up) -- this is the project's first live Slurm coverage, and it already caught a real bug golden tests couldn't (a job's `--output`/`--error` log dir must be created by `submit_slurm` before submission, or Slurm fails the job). Not proven multi-node (single controller+node only). The `slurm` *step* backend (`backends/slurm.py`) was verified against a real cluster too, but its automated coverage is CLI-mocked (`tests/test_slurm_backend.py`), so `pytest` re-checks its argv and parsing rather than the scheduler interaction. Argo Workflows (k8s) and HyperQueue (HPC) are documented future targets, deliberately **not built** until a real cluster needs them (orchestration engines share no spine -- one code path each, so build only on demand). Security: scripts embed **exec-form argv only** (`shlex.join`, never a shell template) and `cab.name`/step-name/sbatch-option keys are charset-validated before interpolation (jobs are named after the **step**, not the cab -- one cab may back many steps, and an unrolled loop always does, so per-cab naming pointed every iteration's `--output` at one file; `cab.name` is still validated even though no longer interpolated, since it arrives from untrusted YAML) (a newline would otherwise inject `#SBATCH` directives); the non-`binary` flavour guard is inherited via `build_argv`. **In-place mutation ordering** (`MutationOrder`) is the one piece of graph knowledge the compiler adds rather than inherits, and it exists because a MUTABLE path leaves *no* trace in the declared graph: `flag`/`gaincal`/`applycal` all take the same MS as a plain input and rewrite it, so `build_graph` sees three independent steps. Locally the default `max_workers=1` hides that behind declaration order; handed to Slurm as an unordered DAG it is data corruption, which is why MUTABLE inputs were refused outright before. They are now allowed for path fields, and the missing edges are derived **from resolved values** -- `Path.resolve()`-canonicalised, compared by equality *and containment* (an MS is a directory, so `/data/obs.ms` and `/data/obs.ms/CORRECTED` are the same data) -- as the compile loop walks steps in declaration order. Two things here are load-bearing. (1) **The predicate is "at least one side declares MUTABLE"**, so read-after-write and write-after-read are ordered too, not just write-after-write: `applycal` mutates while `wsclean` only reads, and a mutator-vs-mutator rule would leave exactly the caracal-shaped case racing. Two pure readers get no edge and stay parallel. (2) **Ordering must be derived from values, not from wiring shape** -- two steps reach one file via an `InputRef` in one and an equal literal in the other, via `./obs.ms` vs an absolute path, or via a schema default neither step mentions; every one of those is syntactically distinct and semantically identical, so any source-matching scheme silently emits no edge. Edges always point backwards (the tracker only ever reports already-recorded steps), which is what lets `submit_slurm` resolve each parent to a job id it has already submitted; a forward one is a hard `OffloadCompileError` rather than a `KeyError` at submission.
- **`ninja run <target> --dryrun`** (`shinobi.dag`): shows the execution graph as a box-drawing diagram, without running anything. `graph_nodes(recipe) -> list[TraceStep]` is a *display view* built on top of `shinobi.graph.build_graph` (so a cyclic/mis-wired recipe raises `RecipeGraphError` at dryrun exactly as it would at execution -- the CLI turns it into a clean `ClickException`); it re-adds a **display-only** edge chaining a dependency-free step after the immediately preceding one, purely so ordering stays visible. The renderer (~130 lines, box-drawing) is kept verbatim from the old model. A bare `Cab` dryrun prints its `build_argv` output. `RecordingBackend` (`shinobi.backends.recording`) covers tests that need to verify calls without executing.
- **Step caching** (`shinobi.cache` + the gate in `_dispatch`): skip a step whose identity (image tag + command/flavour, or an unwrapped `@shinobi.pystep` function's own source), resolved params and upstream provenance are unchanged, and whose declared outputs still exist. Opt-in (`Scope.cache`/`cache_dir`, or `AppConfig.cache`, default **off**). The load-bearing decision is **how a path input is identified**, and it is not one rule but two. A **wired** path is keyed by *the cache key of the step that produced it* -- Merkle-style, bytes never examined -- because a path several steps rewrite in sequence (the caracal2 shape) has no single "current" content, and what a consumer consumed is the state at *its own* point in the chain, which no mtime can express. An **unwired** boundary path is content-fingerprinted as sorted `[relpath, mtime_ns, size]` *plus its path string* (so `cp -a`/`tar -x` copies don't alias), memoized with documented invalidation points. A boundary path the step itself mutates is **dropped from the key entirely** -- otherwise its own previous rewrite would make it look changed forever. Key parts are appended **conditionally** (`__venv__`, `__upstream__`, the content sample), so every scheme extension leaves existing entries keying byte-identically; `tests/test_cache.py` freezes two digests to enforce that. `resources` is deliberately not keyed (it constrains a command, it isn't part of its identity).
- **Per-step sandbox and the replace-on-re-run guarantee** (`shinobi.sandbox`): a step's cwd is a private scratch dir; on success only *declared* outputs (path-typed output fields + `Scope.harvest` globs) move back to the workspace and everything else is swept. That harvest also gives a relative output the guarantee that **re-running a step replaces the previous run's products** -- `_move` replaces the destination wholesale. An output the tool writes *directly* to its destination never went through it: an absolute path, a path-typed input naming a destination (anchored at the workspace by `absolutize_path_inputs`, so the caller's relative spelling doesn't matter), or any output at all when sandboxing is off. It landed on top of the last run -- a hard failure with the CASA family (`mstransform`/`split`/`importuvfits` check the output for existence and refuse) and a silently corrupt product with anything that appends. `clear_stale_outputs` closes that, deleting those destinations *before* the tool starts (it must be before: a refusing tool has already failed by the time anything could harvest). Three things are load-bearing. (1) **Only declared output *fields*** -- resolved by `schema.declared_output_paths`, which `declared_output_dirs` is now built on so the two can't drift. A `harvest`/`scratch` glob's matches were named by the tool at run time and may be workspace data the step never mentioned, exactly why `_move` refuses to rmtree an undeclared directory. (2) **Never a path the step reads**, compared resolved and by containment (`schema.paths_overlap`, shared with the offload compiler's `MutationOrder` -- an MS *is* a directory, so `/data/obs.ms/CORRECTED` and `/data/obs.ms` are the same data, in both directions). (3) **The one case no structural test can decide**: an output field echoing a same-named input is the identical declaration whether the tool *created* that path (`mstransform`'s `outputvis`) or *rewrote the caller's data* in it (`flagdata`'s `vis`) -- `mutated_path_fields` sees one shape, and for a pystep even `Mutability` is unavailable. So the default is the safe reading (echoed = caller's data, never deleted) and a cab opts in once, in its definition, with `ParamMeta.write_path` on the input (`@shinobi.pystep(write_paths=[...])` for the pystep spelling; `field_meta` moved from `Cab` up to `Scope` for it). Do **not** re-derive this from `Mutability.MUTABLE`: it defaults to IMMUTABLE, so a cab that forgot the marker would have its MS deleted -- the polarity has to be opt-in-to-delete. Cost, accepted deliberately: a re-run that then fails leaves neither product (Tier 1 snapshots restore it when on). Escape hatch: `execution.clear_stale_outputs = false`.
- **Mutation-chain snapshots** (`shinobi.snapshots` + `shinobi.clonefs`): what the skip cache structurally cannot do. It keys in-place mutation correctly but cannot *put a state back*, so re-running a mid-chain step executes it against the chain's tip, and resuming after a step died mid-rewrite executes it against its own half-written output -- both **wrong science**, not wasted compute. Tier 1 names each state `(producing step's cache key, producing output field)`, snapshots it, and restores before a step re-runs. Six things are load-bearing. (1) **`cache.ProvenanceKey`** is a `str` subclass carrying `.producer_field`: a leaf step resolves *every* output field to its one `cache_key`, so the key alone cannot name which of two mutated outputs a state is -- and the field must ride along without changing a byte of hashed material, which is why it is a `str` subclass and not a pair. `as_provenance_key` never re-wraps an already-named key, or a state would be renamed at every recipe boundary. (2) **Head status is three-valued** (`trusted`/`untrusted`/`detached`). A single "untrusted" flag conflates a step killed mid-rewrite (the disk is a partial write of a state we can name -- *restore*) with an uncached mutating step having legitimately advanced the disk (good content, no name -- *restoring would revert real work*). Caching is per-scope, so partly-cached chains are normal; conflating these makes Tier 1 destructive exactly there. (3) **The manifest is the success oracle, per run**: `CacheManifest.record` stamps a `run_id` and reconciliation compares it, because there is one entry per step path -- a key match alone means only that *some* run once succeeded, and a step that re-ran (another declared output was deleted) then died mid-rewrite would read its own stale entry as proof it had finished, leaving a permanent cache hit over a corrupt MS. (4) **Chains are keyed by canonical path, not inode**: restore replaces the tree, so an inode key would orphan the chain on every restore -- protection switching itself off precisely when it had just been used. Aliasing (one MS via two paths) is caught by `aliased_chain` instead. (5) **The clone ladder has no hardlink rung**: a hardlinked "snapshot" shares the inode and follows the mutation, so it would reinstate the corruption it was taken to undo. FICLONE → `copy_file_range` (ZFS, probable) → full copy, all in-process, all preserving mtimes (generation 0 is *named* by its fingerprint). (6) **Never worse than shipped**: anything unnameable -- keyless producer, scattered or list-valued mutated field, preflight refusal, missing snapshot, detached chain -- degrades to running against live disk plus a loud warning, never to an unjustified restore. (7) **Reconciliation is gated on `RunPresence`, not on guesswork**: "marker set, no matching manifest entry" reads identically for a corpse and for a run that is simply still going, so a second shinobi would otherwise roll back the first's work mid-write. Each run holds an exclusive `flock` on `snapshots/locks/<run_id>.lock`; reconciliation proceeds only when every other lock file is lockable. Best-effort by design (`flock` silently no-ops on Lustre without the `flock` mount option), so anything unprovable reads as "not alone" and reconciliation is skipped -- safe, because a marker left set still forces a restore on the next run; only the tidying waits. Note also that `snapshots_active` (is Tier 1 on for this *run*) is deliberately separate from `snapshots_enabled` (does *this scope* get a guard) -- conflating them silently disabled crash recovery for every recipe-rooted pipeline. Escape hatch: `cache.snapshots.mode = off`. Tooling: `ninja cache check/invalidate/evict`; `ninja clean --cache` refuses to orphan a quarantined tree without `--force`. Tier 2 (a capacity store, column stripping, cold tiers) is **deferred, not built** -- see `docs/design_cache_tiers.md`.

## Never eval()/exec() a cab's `command`

Cab definitions -- especially YAML cabs in the scabha dialect, of which cult-cargo is the largest published library -- are untrusted content that can carry executable code as data (real cult-cargo cabs exist where `command:` is inline Python/shell source, or a dotted reference to a function to import and call). The full threat model, the guarantees shinobi makes, and the rationale behind them live in [`SECURITY.md`](SECURITY.md) -- read that before touching `shinobi.policies.build_argv()`, the loaders, or the offload script writers.

## Config: one validation library, not five

Stimela 2.0 stacks `omegaconf` + its own `scabha.configuratt` + `munch` + `python-benedict` for config handling. shinobi uses `pydantic` + `pydantic-settings` only -- the same library already used for cab schemas. Precedence, highest to lowest: explicit overrides (CLI) > env vars (`SHINOBI_*`) > config file > built-in defaults. See `shinobi/config.py`.

## Before adding a feature

Ask whether Stimela classic or Stimela 2.0 already solved this, and which one solved it *simply*. If neither did, keep the new piece as small and boring as possible. This project refuses to adopt complexity that isn't earning its keep.

## Reviewing changes: check the tree, not just the diff

When reviewing a PR (or reasoning about any change), verify claims against the actual working tree, not the diff alone. A diff only shows what *changed* -- a pre-existing, unchanged file, symbol, or config target does not appear in it, so its absence from the diff is **not** evidence it doesn't exist. Before asserting that something is missing, dead, unused, or unreferenced, confirm against the repo: `git ls-files <path>`, `ls`, or `grep -r` over the checkout. Concretely: PR #1's automated review called `docs/conf.py`'s `exclude_patterns` entry for `docs/design_sandbox.md` "dead config, file doesn't exist" -- but the file is tracked and load-bearing (it stops Sphinx warning that the unlisted markdown isn't in a toctree); it just never showed up in the diff because the PR didn't touch it. Look at the tree.

## Attribution: commit trailers yes, PR trailers no

A commit made with an assistant's help says so in a trailer on the
**commit message**, naming the assistant and the model behind it:

```
Assisted-by: <LLM> <MODEL>
```

-- e.g. `Assisted-by: Claude Opus 5`, `Assisted-by: Codex GPT-5`. One
line, last in the message, after any `Co-authored-by:` for real people.

Agents default to a `Co-authored-by:` trailer with an address; replace
it. Both halves of that default are wrong here. `Co-authored-by:` claims
more than happened -- these tools assist, and the person who ran them
owns the change and answers for it. The address is what makes the claim
bite: GitHub renders a trailer as co-authorship only when one is
present, so `Co-authored-by: Claude <noreply@anthropic.com>` attaches a
vendor to the authorship of work this organisation owns. `Assisted-by:`
with no address records the same fact as plain text and attaches nobody.

This reverses the rule as it stood until August 2026, which argued that
co-authorship was the honest description of tools doing real work. The
consideration that changed it is ownership, not accuracy of credit:
these are paid services operating on our IP, and the history should not
carry anything a vendor could read as a stake in it.

**Pull request descriptions carry no trailer at all** -- no
`Assisted-by:`, no `Co-authored-by:`, no "Generated with", no tool
badge. A PR body is review material: it exists to tell a reviewer what
changed and why, and what to check. Provenance already lives on every
commit the PR contains, where it is attached to the specific change
rather than repeated once per PR, so a trailer in the description is
duplication in the one place that has no room for it. Agents default to adding one; delete it.

Neither form is a substitute for the message itself. A commit that
explains a decision badly does not improve by naming the model that
helped make it -- see the existing history for the standard: what
changed, what it deviates from and why, and what a reviewer should not
assume held still.
